# BioGuard X API integration contract

## Implemented integration status

The Vanilla JavaScript enrollment and verification modules are connected to the experimental FastAPI adapter in api/main.py when BIOGUARD_API_BASE is configured. The UI does not invent routes. It uses the three routes listed below and the multipart field names implemented by the backend.

When no API URL is configured on any host, the modules enter an explicit demo-preview mode. Local API mode must be opted into by setting BIOGUARD_API_BASE to the local API origin. File inputs are not rendered, no biometric sample is transmitted, and no identity or verification result is fabricated. If an API URL is configured but the service fails, the UI shows an error; it does not silently fall back to demo success.

## Implemented routes

| Method | Route | Frontend use |
|---|---|---|
| GET | /api/v1/health | Checks API, database, and encryption configuration |
| POST | /api/v1/identities/enroll | Creates an identity record and stores encrypted experimental feature templates |
| POST | /api/v1/verification/multimodal | Compares submitted features when compatible enrollment templates and a trusted trained bundle exist |

All POST requests require an Authorization: Bearer operator-token header. The token is requested at submission time, kept in page memory only, and never written to local storage or config.js.

## Multipart request contract

Enrollment:
- profile: JSON object with full_name, identity_ref, and optional email
- modalities: JSON array containing one or more of face, voice, fingerprint
- consent: JSON object with granted=true and a policy_version string
- face_sample, voice_sample, fingerprint_sample: file parts for the selected modalities only

Verification:
- claimed_identity_ref: enrolled identity reference
- modalities: JSON array containing one or more supported modalities
- authorization: JSON object with authorized=true and a purpose string (3–200 characters)
- face_sample, voice_sample, fingerprint_sample: file parts for the selected modalities only

The frontend checks required fields, modality selection, file extension/MIME, and size (face/fingerprint 10 MB; voice 20 MB). The API remains responsible for authoritative validation, decoding, and processing.

## Result and safety contract

- Enrollment success means the experimental API created an identity row and encrypted handcrafted feature templates. It does not mean a validated biometric identity model was created.
- Verification may return match, no_match, or not_evaluated. Model output is experimental and diagnostic only.
- policy_decision remains pending. No API response grants or denies access, and the frontend never renders a risk score.
- Raw uploads are processed in memory; metadata-only audit events are written. Encrypted feature vectors are stored in SQLite.
- The browser consent/authorization acknowledgements are not substitutes for legal authority, operator authentication, or server-side policy controls.

## Model compatibility and limitations

- Face: HOG + LBP baseline features.
- Voice: MFCC-style statistics + zero-crossing rate + RMS.
- Fingerprint: multi-orientation Gabor texture statistics.
- A trusted versioned model bundle is required for experimental comparisons. Without the compatible modality models, verification returns not_evaluated.
- No face detection/alignment, liveness/spoof detection, calibrated risk score, production identity-provider integration, rate limiting, managed key lifecycle, retention/deletion workflow, HTTPS deployment hardening, or independent security review is implemented.

Never load an untrusted joblib artifact: pickle-based model bundles can execute code. Configure BIOGUARD_MODEL_PATH only to a trusted artifact generated by this project.
